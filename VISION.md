# Kani UI vision — from-scratch research prototype

The first target is screenshots, applications and code editors. The implemented
model predicts six **coarse region classes**: background, toolbar, sidebar, editor,
terminal and dialog. It returns an 8×8 grid for a 96×96 RGB input. This is a working
training/inference path, not yet a general vision-language assistant.

## Architecture and implementation

`kelus/vision.py` implements RGB patches → learned linear projection and position
embeddings → two bidirectional transformer encoder blocks → a per-patch region
head. Attention has no causal mask. Width is 48 with four heads. Parameters start
randomly; our `Tensor` autograd, cross-entropy and AdamW train them. NumPy provides
array arithmetic. Pillow only decodes/resizes images. There are no pretrained
weights or ML frameworks. The patch-transformer design follows the general
[Vision Transformer architecture](https://arxiv.org/abs/2010.11929).

The model is separate from the language checkpoint. It does **not** add image tokens
to the text model, perform OCR, generate descriptions, locate precise click targets,
read code, or control the computer. Those capabilities still require labeled data,
an image/text interface, training and independent evaluations.

## Run it

From the repository directory:

```sh
python3 -m pip install -r requirements-vision.txt
# Small synthetic UI smoke training; default 400 steps, never touches text weights.
OPENBLAS_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1 python3 -m kelus.vision train
python3 -m kelus.vision inspect --image screenshot.png --out regions.json
# Or from the CLI, with the image inside its selected workspace:
kani "/vision screenshot.png"
```

`--out checkpoints/vision-ui.npz` selects the training destination; `--checkpoint`
selects weights for Python inspection. Kani accepts `--vision-model FILE` and
`--python CMD`. Inspection letterboxes the image and records original/resized size
and offsets. Grid coordinates refer to that letterboxed image, not directly to
screen pixels. Displayed probabilities are uncalibrated.

The default synthetic corpus is generated locally with original procedural UI
layouts, randomized colors, line textures and noise. Training and validation use
different seeds. High scores on these simple generated patterns establish that
optimization works; they **do not measure performance on real app screenshots**.
A third seed is used for the smoke report's independent synthetic test split.
Results are in `reports/vision-ui-smoke.json`; local weights stay in `checkpoints/`.

A separate rendered-page experiment is also present locally at
`checkpoints/vision-ui-render.npz` (generated by `data/make_ui_screens.py`). Its
best validation-loss checkpoint, step 1,400, reports **0.331 mean IoU** and **66.9%
patch accuracy** on its held-out layout family. These are generated HTML pages,
not real application screenshots. This much lower result shows why the simple
procedural smoke score is not evidence of general vision ability. Select the
experimental weights explicitly with `--vision-model`; defaults are unchanged.

## Train on annotated screenshots

Use consented/licensed screenshots and label the corresponding pixels with a
single-channel PNG mask, values 0–5 in the class order above. Each mask must have
the same dimensions as its screenshot. A JSONL manifest contains:

```json
{"image":"images/editor-a.png","mask":"masks/editor-a.png","split":"train"}
{"image":"images/editor-b.png","mask":"masks/editor-b.png","split":"validation"}
```

Include at least two distinct images in each split. Paths are relative to the
manifest. Duplicate image files and train/validation overlap are rejected. Split
by app/session/layout before augmentation, rather than putting neighboring frames
in both sets. The loader letterboxes images and masks together and assigns the
majority class to each patch.

```sh
python3 -m kelus.vision train --data data/ui/manifest.jsonl --steps 2000 \
  --out checkpoints/vision-real-ui.npz
```

This starts from random weights. The best validation-loss checkpoint is saved
atomically; its adjacent `.report.json` records the run. This initial trainer does
not resume optimizer state. Scores include per-class intersection-over-union,
mean IoU, a confusion matrix, and patch accuracy (which can hide class imbalance).

## Next research milestones

1. Collect and annotate diverse real screenshots across apps, themes, languages,
   displays and scale factors; reserve unseen apps for final testing.
2. Measure real region IoU and calibration. Increase resolution/capacity based on
   observed errors. A 96-pixel input is much too small for reading code.
3. Add text detection/recognition and screenshot/question/answer training data.
4. Train a projection between the image encoder and our text model, then train
   multimodal instruction following. Check that language/coding ability survives.
5. Evaluate unseen screenshot questions, grounded locations and coding tasks before
   considering any action-taking integration or capability claims.

Passing this smoke test does not demonstrate deep reasoning or superiority to any
other assistant. Such claims need direct, reproducible evaluations.
